# WordPress passthrough — how a post and a page reach the browser

How `/<id>/` (posts, films) and every non-numeric path (WP pages) are served, what lives on the WordPress side, which stylesheets meet in the rendered body, and the bugs that came out of it.

Companion docs: [`legacy-page-fallback.md`](./legacy-page-fallback.md) for the A6 iframe underneath this, [`wp-backend.md`](./wp-backend.md) for the WP content model, [`implementation-notes.md`](./implementation-notes.md) §D6b for the build record.

## 1. One route, two branches

Everything below is `app/[...slug]/page.tsx`. It splits on the shape of the slug and nothing else:

```
/<id>/            → numeric, single segment  → post or film
anything else     → WP page → legacy iframe → 404
```

### Posts and films — `/<id>/`

1. `resolvePostKind(id)` probes `/wp/v2/posts/<id>?_fields=id,format`. Raw `wpFetch`, not the typed client: a 404 is an expected answer here, and the client's middleware turns non-2xx into a throw. Wrapped in `cache()`, so `generateMetadata` and the page share one round trip.
2. `format === 'video'` → `modules/Video/FilmPage`; anything else → `modules/News/NewsArticle`.
3. `generateStaticParams` seeds 20 films + 20 posts, `dynamicParams = true`, `revalidate = 3600`.

There is deliberately no `/news/<id>` or `/video/<id>` — see `CLAUDE.md`.

### Pages — every other path

1. `isEmbeddable(slug)` — a path-shape guard that runs **before any fetch**, so `/favicon.png/` and `/legacy/…` cost nothing.
2. `isLegacyEmbedPage(path)` — the opt-out list in `shared/config/legacyEmbedPages.ts` (20 paths). A listed path goes straight to the iframe.
3. `cachedFetchWpPage(path)` — WP REST has no lookup by path, so this queries `?slug=<last segment>&per_page=10` and then **verifies `link` against the requested path**. Without that check `/materials/plakati/` and a top-level `/plakati/` would answer for each other.
4. A page → `modules/WpPage`. No page → `LegacyEmbed`, the A6 iframe over `WP_LEGACY_BASE`.

**Opt-out, not opt-in.** ~150 pages came online with nothing to configure, a newly published WP page is live at its URL without a deploy, and no URL changes — entries and rankings are untouched. The cost is one WP request on paths that turn out not to be pages, cached for an hour under the `wp:pages` tag and bounded by the route's ISR window.

`sitemap.ts` enumerates `/wp/v2/pages` separately (two requests). It has to: the live sitemap is generated by a WP plugin, which 404s the moment the frontend takes the domain.

## 2. Is a page rendered differently from a post?

**The content pipeline is all but identical.** Both run `resolveContentImages(html)` → `parsePost` → `<GutenbergProvider>`. One deliberate difference since 2026-08-17: `parsePost`'s hero lift — the first carousel/gallery pulled out into a separate `header` slot — is **on for posts and films, off for pages** (`liftHeader: false`). It removes the matched block's whole *parent*, which is the migrator's wrapper on a post and an editor's column on a page; measured over od-dev's 170 pages, both of the two that carry a gallery would lose a sibling and neither has one to lift. Rationale in [`wp-page-redesign.md`](./wp-page-redesign.md).

Only the furniture around it differs:

| | `NewsArticle` | `WpPage` |
| --- | --- | --- |
| Title | in the body (WP posts carry an in-body H1) | `PageHeader` on top — a WP page's title lives outside `content` |
| Header slot | above the date | none — the lift is off, the block stays in the body |
| Date | yes | no |
| Sidebar | `SimilarNews` + `NewsletterSignup`, sticky | none, body is full width |
| Nav | `Breadcrumbs` | `PageHeader`'s breadcrumbs |

So when a page renders wrong and a post doesn't, **the difference is in the content, not in the renderer**. Measured 2026-08-16 over od-dev:

| | total | carry an inline `<style>` | `<style>` positions something absolutely |
| --- | --- | --- | --- |
| posts | 8 241 | 2 247 (27 %) | **0** |
| pages | 174 | 30 (17 %) | **7** |

Posts bring plenty of author CSS; none of it positions anything. Pages do, because the section index pages were hand-built as tile grids under the old theme. That is the entire asymmetry.

The seven pages, and whether they reach this renderer at all:

| Page | selectors | served as |
| --- | --- | --- |
| `/materials/printed-products/` | `.textcapt` | **native** |
| `/materials/social-reklama/` | `.textcapt` | **native** |
| `/get-involved/share-knowledge/` | `.descr:after` | **native** — but `.descr` is itself `position: relative`, so it anchors correctly on its own |
| `/get-involved/` | `.textcapt`, `.smallcapt` | iframe (in the opt-out list) |
| `/get-involved/join/` | `.b-close`, `.btn .plus` | iframe (in the opt-out list) |
| `/materials/` | `.textcapt` | never reached — `app/materials/page.tsx` takes precedence |
| `/video/famous-people/` | hover effect | never reached — `app/video/[segment]/page.tsx` takes precedence |

## 3. Where the styles come from

Three sources meet inside `.gutenberg`, in cascade order:

1. **`@wordpress/block-library`** — `style.css` + `theme.css`, the block defaults.
2. **`gutenberg.css`** — our typography over the top: headings, `p`, lists, links, buttons, tables, plus the carousel CSS.

   Both are pulled in by `gutenberg-provider.css` through `@nested-import`, so everything is nested under `.gutenberg` and cannot leak into the rest of the site.
3. **The page's own `<style>`**, which arrives inside `content.rendered` and lands in the DOM as-is. It is **unlayered, unscoped author CSS** — it competes with (1) and (2) on ordinary specificity, and it was written against a theme that no longer exists.

The old CMSMasters theme is not loaded anywhere on the frontend. Everything the author CSS assumed about its markup — positioned columns, `.image` wrappers, `cmsms_*` classes — has to be either supplied by us or given up.

## 4. Bugs, and where each was fixed

**Every image 404ed.** The block editor writes `src="/wp-content/uploads/…"`, root-relative, which resolves against *our* origin. Fixed in `resolveMediaUrl`, which now gives a root-relative or protocol-relative src the WP origin before anything else — so every caller benefits, not just page bodies.

**The lightbox had never worked, on any page.** `ImagePreviewClient` attached handlers by walking `children` with `cloneElement` — passes a unit test, finds nothing in a browser, because the content crosses a Server Component boundary a client component cannot introspect. Measured: 0 of 19 images on a news post carried the handler. Rewritten as one delegated listener on a wrapper. The first diagnosis, "missing `preventDefault`", was a symptom of the same thing: the click was never handled, so WordPress's wrapping `<a>` simply navigated — to a 404, that href being root-relative too.

**Once it opened it would not close.** The dialog was a fixed 90vw × 90vh box with a `fill` image letterboxed inside, so the grey beside a portrait picture was *dialog*, not overlay, and the natural place to click to dismiss hit nothing. The panel is now `width: fit-content`, sized from the clicked thumbnail.

**Captions flew to the top-left corner of the document.** `/materials/printed-products/` and `/materials/social-reklama/` lay a caption over each tile with `.textcapt { position: absolute; top: 15px; left: 17px }`. An absolutely positioned element needs a positioned ancestor; the old theme's `.cmsms_column` was one, Gutenberg's `.wp-block-column` is `static`, so every caption resolved against the initial containing block and stacked over the site header, leaving the pictures captionless.

Fixed in `gutenberg.css` with the parity rule:

```css
.wp-block-column {
  position: relative;
}
```

**Then the captions came back grey.** The page colours the *column* (`.redcapt`); our `.wp-block-columns p { color: var(--gray-7) }` matched the paragraph itself, and an inherited value always loses to a rule matching the element. The rule is deleted — its `font-size` only duplicated the base `p` rule, so colour was all it did, and a page's own styling should win inside its own body.

### Why the positioning rule is safe, and why it is a rule rather than a page edit

Checked before shipping it:

- `position: relative` with `z-index: auto` creates a **containing block**, not a stacking context. Nothing is re-layered by it, and a column with no offsets renders identically.
- The only elements it can re-anchor are absolutely positioned descendants of a column whose nearest positioned ancestor used to be further out. In our own CSS there are none: `grep -rn "position: *absolute" src/shared/ui/theme/gutenberg/` returns zero rules.
- `@wordpress/block-library` uses absolute positioning inside cover, navigation and similar blocks — each of which sets `position: relative` on its own container. A nearer positioned ancestor wins, so those are untouched.
- Author CSS: 7 pages, of which 3 reach this renderer, of which one (`share-knowledge`) already positions its own parent. The two `.textcapt` pages are the only elements the rule moves, and it moves them where the old theme had them.
- Posts: 0 of 8 241.

**It is a rule and not a hand-rebuild of the two pages** because the same content migrates to prod the same way — `cmsms-gutenberg-upgrade` will bring the same `<style>` blocks with it — and because the failure mode is disproportionate: a caption that escapes its column lands on top of the site header, on a page nobody edited. One three-line parity rule restores the contract the markup was written against; rebuilding one page leaves the next one to break the same way. The two pages still want content work (§5), just not for this reason.

## 5. The migrator dropped every image link — fixed at the source

**Symptom, on the two tile pages:** each tile's `<a>` pointed at `/wp-content/uploads/….jpg` where the live site links to the child page (`/materials/books/`, `/zakladki/`, `/booklet/`, `/disk/`, `/autosticker/`). So a tile opened the lightbox instead of navigating, and the grandchild pages lost their only inbound links. The tiles had also gone white and full-brightness instead of the live site's grey dimmed panels.

**Cause, in `cmsms-gutenberg-upgrade`:** its `cmsms_image` branch matched `\[cmsms_image[^\]]*\]` and threw the attributes away, hard-coding `linkDestination:"media"` with the image's own URL as the href. The original shortcode carries both facts:

```
[cmsms_image align="center" link="/materials/books/" classes="image colorize"]38201|/wp-content/uploads/…jpg|full[/cmsms_image]
```

`link` is the destination; `classes` is what the page's own `[cmsms_css]` styles (`.image { background: #cdcdcd; border-radius: 10px }`, `.image img { opacity: .4 }`, `.image:hover img { transform: scale(1.15) }`). Both were dropped, which is why one bug produced two symptoms.

**Scale, measured 2026-08-16 across od-dev:** **5 825 links** on **2 824 published records** — 24 pages, 2 758 posts, 42 profiles. Not two pages. Breakdown of the destinations: 5 467 point at *another* image file (a thumbnail linking to its full-size original — the lightbox pattern, which our `ImagePreviewClient` handles by `img.currentSrc` either way, so those were harmless in practice), 296 at the same file, and **~60 are real navigation** — internal paths such as `/get-involved/give-a-lesson/` and a page of ~30 partner sites on post 20118.

**Fix:** the converter now parses the attributes, keeps `link` as the href (`linkDestination:"custom"` when it differs from the image, `media` otherwise) and carries `classes` onto both the block attributes and the `<figure>`. Source and CLI in §6.

Applied to the two tile pages on od-dev (`wp cmsms migrate --post=57271,57269`) and verified in a browser at 1440: grey panels, red captions over the pictures, tiles navigating to their child pages. Two cosmetic differences from the live site remain, both ours rather than the content's: the picture sits left instead of right (the page says `text-align: right`, our `gutenberg.css` says `img { display: block }`), and panels in a row are equal-height (Gutenberg columns are flex; the old theme floated them). Not worth emulating a dead theme for.

**Run across all of od-dev on 2026-08-17** — not because posts needed it (on a post the restored link is almost always a thumbnail pointing at its own full-size original, and the lightbox intercepts anything under `/wp-content/uploads/` and displays `img.currentSrc` regardless, so nothing rendered differently), but because **prod migrates in full at cutover**: od-dev has to be the content prod will have, or it is testing something else. Re-running is safe by construction — `migrate` always converts from the `nvp_content_copy` backup, never from the current body. 2 657 records changed, 5 821 were already identical; a second dry-run afterwards reported 0 left, which is the convergence check.

**The bulk run is what found the link shapes a two-page sample never would.** `esc_url()` prefixes `http://` to any value with no scheme and no leading slash, so three link shapes needed handling before the restored href was an improvement:

| In the shortcode | `esc_url()` gave | Now |
| --- | --- | --- |
| `printed-products` (a bare relative slug, on `/materials/`) | `http://printed-products` — a nonexistent host | left relative, resolves to `/materials/printed-products` |
| `wp-content/uploads/…jpg` (no leading slash) | relative to the post's own URL | `/wp-content/uploads/…jpg` |
| `i/wp-content/uploads/…jpg` (a typo, 3 posts) | `http://i/wp-content/…` — host `i` | `/wp-content/uploads/…jpg` |

The first is escaped with `esc_attr` instead of `esc_url` (no colon can reach that branch, so `javascript:`/`data:` cannot either); the other two are normalised to the root path — only when the value has no scheme and is not already absolute, so a link to another domain is never rewritten. Without the normalisation those hrefs would also miss `ImagePreviewClient`'s `/wp-content/uploads/` test and navigate somewhere broken instead of opening the lightbox.

Not fixed, because it is not ours: profile 21157 carries `href="http://+7-903-722-53-29"` **in the original body** — someone typed a phone number into WP's link field years ago. Content junk on a record no route renders yet.

**WooCommerce shortcodes are handed over unexpanded.** REST returns `[woocommerce_cart]` verbatim — only the theme expands it, so the four shop pages had to stay on the opt-out list. They were deleted instead; see §7.

**Cyrillic slugs never match.** WordPress stores them percent-encoded and we compare paths decoded, so those pages fall through to the iframe. Deliberate: matching both forms costs two round trips on every miss, to serve pages with no measurable traffic.

## 6. Running the migrator

`cmsms-gutenberg-upgrade` converts CMSMasters shortcodes to core Gutenberg blocks. It ran once on od-dev; **prod runs it as part of the cutover**, so a bug in it is a bug in prod's future content, which is why the fix above went here rather than into the two pages.

**Its source now lives in this repo** — [`wp/plugins/cmsms-gutenberg-upgrade/`](../wp/plugins/cmsms-gutenberg-upgrade/) — on the same terms as `wp/mu-plugins/od-revalidate.php`: edit here, upload with `scp`, one copy to review. The original author (Николай Воронков) is not shipping updates; we own it until it is deleted with cmsms after cutover.

```bash
scp wp/plugins/cmsms-gutenberg-upgrade/cmsms-gutenberg-upgrade.php \
    timeweb:od-dev/public_html/wp-content/plugins/cmsms-gutenberg-upgrade/
```

**WP-CLI, so a migration can be run and reviewed from a script instead of clicked through the admin page.** Every subcommand needs `--url=` on this install: clearfy-pro redirects to HTTPS on `init`, and without a host WP-CLI dies before WordPress finishes loading.

```bash
cd ~/od-dev/public_html
wp cmsms backup  --url=https://od-dev.tmweb.ru        # originals → nvp_content_copy meta (idempotent)
wp cmsms migrate --url=… --post=57271 --dry-run       # what would change, nothing written
wp cmsms migrate --url=…                              # every record that has a copy
wp cmsms restore --url=… --post=57271                 # roll back from the copy
wp cmsms dump 57271 --url=… [--original|--converted]  # for diffing before/after
```

`backup` is what makes the rest reversible: the pre-migration `post_content` is kept in the `nvp_content_copy` meta, `migrate` always converts *from that copy* (so it is re-runnable after a converter fix), and `restore` puts it back. The CLI writes through `$wpdb->update` rather than `wp_update_post` on purpose — the plugin's own `save_post` hook deletes `nvp_content_copy` on update, which would destroy the copy both re-running and rollback depend on. A revision is saved before each write.

The four admin-page buttons still work and do the same four things.

## 8. When a page renders wrong

In order, cheapest first:

1. Is it native or iframed? A native page has a `PageHeader`; the iframe is a `<iframe src="/legacy/…">`. Check `legacyEmbedPages.ts`.
2. Read the page's own `<style>` in `content.rendered`. It is unscoped author CSS and it is usually the answer.
3. Compare against the live site's markup for the same page — the old theme's class is normally what the CSS expects (`.cmsms_column` → `.wp-block-column`, `.image`, …).
4. Only then look at `gutenberg.css`. A rule of ours that matches an element directly beats any colour or size the page inherits down to it.
5. If the fix is a parity rule (something the old theme supplied that Gutenberg does not), it belongs in `gutenberg.css` — the same content is coming to prod through the same migrator. If it is a broken link or a lost class, it is content, and it belongs in WordPress or in `cmsms-gutenberg-upgrade`.
